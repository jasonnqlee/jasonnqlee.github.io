Pipework Python Automation Scripting Suite

Automated and improved traceability process for piping paperwork
@ SLB Schlumberger (Labuan) Reservoir Performance Testing Intern (5/26-8/26)

Outcome

~10x faster per asset · 40+ hours saved per 500-pipe job · 204,000+ assets supported · built for the wider East Asia Group

At SLB, I was a Reservoir Performance Testing intern responsible for equipment traceability — tracking hundreds of unique parts across every job, for every client, in our department's TestTrack database. Over half of any job's parts were pipework, tracked the same way every time, but TestTrack only let you search and update pipes one at a time.

With one upcoming job involving over 500 pipes, doing this by hand wasn't just slow — it was the largest single time cost in my role. I built a suite of Python tools that read directly from Excel, drive TestTrack through the browser, and manage pipes in batches instead of one by one.

Manually, searching and checking 540 pipes took roughly 22.5 hours. The automated version does the same work in about 1.3 hours — and that's before counting the downstream steps (asset creation, editing, UT upload) it also automates.

Experience, Learnings, and Skills

Not every part of this toolkit was automated the same way — and deciding where to draw that line was one of the more important calls I made on this project.

Searching for a pipe, checking its inspection status, and downloading its report is low-risk: if something goes wrong, you just run it again. So the SL3 search and download tool runs fully unattended — log in once, then it works through hundreds of serial numbers without needing me to watch it.

Creating a new asset is a different kind of risk. Very few people at SLB have permission to delete a wrongly created pipe once it exists in TestTrack — a mistake there isn't just annoying, it's hard to undo. So that tool runs semi-automated: it pre-fills every field from the Excel sheet, including the asset code, the born-on/commissioned/in-service dates, and the matching COC file — then it waits, giving me an hour to actually check the fields before clicking submit myself. I only turned off that review step once I'd verified the asset-code logic was solid across enough real cases to trust it.

That's the pattern across all four tools: automate the repetitive, low-stakes parts completely; keep a human check exactly where a mistake would be expensive or irreversible.

I also built in recovery for the boring failure modes that inevitably show up over a multi-hour run — the workbook saves every 9 rows, so a crash or a lost connection partway through a 500-asset job doesn't mean starting over. Searches that don't find an asset immediately retry, then fall back to checking across all accounting units, then check whether the asset is simply decommissioned, before giving up and flagging it for manual review. Stale references in the browser (a common Selenium failure when a page updates mid-action) get caught and retried automatically rather than crashing the whole run.

The tools also don't blindly trust their inputs. The UT upload tool cross-checks the serial number embedded in each PDF against the serial number in Excel before using it — if a report doesn't match, or a PDF exists in the folder with no matching serial number at all, it gets moved into a separate "Non Relevant PDFs" folder rather than silently processed or ignored.

All four tools share the same underlying search-and-login logic, refactored so I wasn't rewriting the same TestTrack automation four times. What started as one script for one job became a small internal toolkit.

I also built the search-and-process step to run in parallel across multiple worker sessions — splitting the input workbook, running several TestTrack sessions at once, then merging the results back into one file. It currently runs in single-session mode; I got the architecture working but haven't yet had a large enough job, or enough confidence in TestTrack's tolerance for concurrent sessions, to rely on it in production. It's there for when the job size justifies it.

Motivations

Reservoir performance testing wasn't the industry I expected to end up in, and my assigned role — equipment traceability — was mostly manual, repetitive record-keeping. It wasn't glamorous, but it was necessary, and I noticed early on that it was taking up a disproportionate share of my time relative to how complex the work actually was.

Rather than treat that as just the job, I saw it as a chance to build something. Automating the parts of my own role that didn't need a person freed up time for higher-value work, and gave the rest of the department — current interns and future ones — a tool they could use too.

Technical Details

The toolkit is four separate Python scripts, each handling one stage of a pipe's lifecycle in TestTrack: searching and downloading SL3 inspection reports, uploading UT thickness readings, creating new assets, and editing existing ones. They share a common foundation — the same login flow, the same asset-search logic, the same fallback behavior when an asset isn't found in the default accounting unit — refactored across files rather than rewritten each time.

Search and Retrieval

The SL3 tool reads a list of serial numbers from Excel and, for each one, searches TestTrack, checks whether an SL3 (major inspection) report exists, and flags cases where an inspection is still in progress rather than complete. Since a pipe can go up to five years without reinspection after a Major inspection, knowing the most recent SL3 date at a glance is what actually matters for planning — so the tool extracts that date, generates a renamed PDF copy of the report, and writes the date back into Excel automatically.

If an asset isn't found under the default accounting unit, the tool doesn't just report a failure — it checks whether the asset is decommissioned first, then retries the search across all accounting units before giving up. That ordering matters: a decommissioned asset and a missing one need different follow-up, and getting them confused would send someone chasing the wrong problem.

Manual retrieval of SL3 certificates averaged about 2 minutes per asset, measured by timing a new intern doing it by hand. The automated version runs at roughly 10–15 seconds per asset, depending on network conditions — about a 10x speedup, and around 15 hours saved on a 500-asset job alone.

Validation and Data Integrity

The UT thickness upload tool reads inspection PDFs with pdfplumber, extracts the thickness readings at each measurement point, and determines whether the result is Accepted or Rejected — but only after validating that the serial number embedded in the PDF actually matches the serial number in Excel. Reports that don't match a serial number in the input list get moved into a separate "Non Relevant PDFs" folder automatically, so they're never silently misapplied to the wrong asset.

The parsing logic currently supports reports with up to four measurement points (A–D); reports with additional columns need an update to the extraction logic — a known limitation I documented rather than tried to silently work around.

Risk-Tiered Automation

Not every tool in the suite runs the same way, and that was a deliberate choice rather than an oversight. Searching, checking status, and downloading reports is low-risk and fully reversible — if something goes wrong, you just rerun it — so that tool runs unattended from login to completion.

Creating a new asset in TestTrack is a different kind of risk: very few people have permission to delete a wrongly created asset once it exists. So the asset creation tool pre-fills every field — serial number, asset code, born-on/commissioned/in-service dates, and the matching COC upload — then pauses for up to an hour, waiting for a human to actually check the fields before submitting. I only switched off that manual review step once I'd validated the asset-code-generation logic against enough real cases to trust it unattended.

Resilience

A run against hundreds of assets can take hours, so I built in recovery for the ordinary failure modes that come with a long unattended process: the workbook saves progress every 9 rows, so a crash or lost connection doesn't mean starting over from row one. Stale element references in Selenium — a common failure when TestTrack's page updates mid-action — are caught and retried rather than allowed to crash the whole run. Every asset that fails for any reason gets logged with its own error and status flag in Excel, rather than halting the batch.

Built for Scale, Not Yet Fully Exercised

The search-and-process pipeline also includes a parallel-processing path: splitting the input workbook across multiple worker sessions, running several TestTrack logins concurrently, then merging the results back into one file. It currently runs in single-session mode — I built and tested the architecture, but haven't yet had a job large enough, or enough confidence in how TestTrack handles concurrent sessions at scale, to rely on it in production. The scaffolding is there for when it's needed.

Improvements

Given more time, I would have liked to:

  • Complete the automatic UT thickness reading upload — the extraction and validation logic is built, but the final upload step is still partially implemented
  • Extend PDF parsing to support inspection reports with more than four measurement points
  • Replace fixed delays with fully explicit waits throughout, to make the automation more robust to TestTrack's own loading behavior
  • Add resume-from-last-successful-asset recovery after an unexpected interruption, rather than relying only on periodic saves
  • Validate and enable the multi-session parallel processing path on a real large-scale job
